## 语料与方法

两个语料相差 3 条记忆：基线有 40 条，数据仓是 2026-10-20 的 37 条导入快照，缺少 `memorytree-m0-status`、`memorytree-m1-index`、`memorytree-m1-mcp`。因此 20 题只使用两边都存在、且结论未随时间变化的事实；技能数量、7-Zip 去留、AiraDock 续作入口、BrowserSkill 扩展状态等两库已不一致的细节被刻意避开。最初两题涉及新增记忆（Go 安装路径、AiraDock 最新续作入口），MemoryTree 返回 0 命中，属于语料滞后而非检索失败，已替换为语料内问题。

MemoryTree 流程：`memory_search`（`limit=5`）→ 摘要足够则停止；摘要不足以回答时 `memory_get` 带具体事实关键词和 `max_chars=1200` 取片段。13 题需要 `memory_get`，其中 10 题触发片段，3 题因正文不超过 1200 字符仍返回全文。token 为各次响应 `meta.tokens_estimated` 之和，只统计 `data`，与 MCP 的估算口径一致（ASCII 0.25，非 ASCII 1）。

基线流程：读 `MEMORY.md`（2,879 token）→ 不足时 `grep -n -C 3` 命中文件；本轮所有 grep 输出都足以回答，无需整文件读取。

MCP `tools/list` 的工具定义约 875 token，属于一次性会话开销，未计入上表。

## 发现

1. **两项修复都产生了预期效果**。首条命中从 19/20 到 20/20；`memory_get` 片段把 13 次读取的总成本从 27,904 降到 9,208 token，Q13 降幅 89%。
2. **剩余噪音成本很低**。Q1、Q18 等查询仍会带回 2–4 条摘要，但首条都正确，整题 token 仍在 1.2k 以内；暂时不值得为排序再增加复杂度。
3. **片段模式的行为需要按正文长度理解**。正文不超过 `max_chars` 时不会截断，Q7/Q8/Q20 因此仍是全文；只有长正文才产生 token 节省。query 未命中正文时返回开头并警告，Agent 可据此决定是否改用全文模式。
4. **数据新鲜度仍是真实使用的主要风险**。3 条导入后新增的记忆不在数据仓，相关问题的首次检索为 0 命中。检索层无法修复语料滞后，需要 M2 写入路径或受控重新导入。
5. **摊薄口径基本持平，规模化优势尚未证明**。37 条语料的 `MEMORY.md` 只有 2,879 token，精确 grep 仍然便宜；MemoryTree 现在只高约 12%。需要 100 条以上语料复测，才能验证索引成本线性增长后 MemoryTree 的交叉点。

## 建议

1. M2 落地后，用写入路径或受控重新导入补齐 3 条新增记忆，重跑本轮排除的“新鲜度”问题。
2. 在 100 条以上语料、真实 Qoder 客户端会话中复测，并单独记录 `memory_brief` 的预算内表现；未来验收继续区分“每题独立会话”和“同会话摊薄”两种口径。
3. 人工评分请用户抽检上表，尤其 Q18；确认后把 M1 标记为最终验收完成。
4. 暂不继续优化排序或片段默认值；先把写路径和语料补齐，再根据更大语料决定是否需要调整。

## 验收结论

检索功能与效率均达到验收线：20/20 完整回答、20/20 首条命中；每题独立会话 14,723 vs 67,796 token（约省 78%），同会话摊薄口径与基线基本持平。首轮发现的两项问题已修复并有回归测试。人工评分 4.95 已确认（2026-10-26）；数据仓缺 3 条新记忆的问题转入 M2。
